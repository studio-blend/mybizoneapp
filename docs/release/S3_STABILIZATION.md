## Supported behavior and limits

- Owners and business-wide role holders can use the gates assigned in the domain permission matrix. Granting a role does not confer permissions outside that matrix.
- Store-scoped sales/billing staff can use assigned-store POS, sales lists/details/CSV, bill files and invoice operations. Scoped POS supports walk-in sales; supplying a registered customer requires an unscoped sale grant because customer balances and EMI accounts are shared across the business. Customer-linked returns require the same unscoped grant. A role can contain more than one explicit store grant.
- Store-scoped inventory staff can list/create/edit products and access product images within authorized stores. Product moves require permission for both old and new stores. Category options are limited to authorized stores or shared categories; shared brand names are available for product assignment.
- Business-wide reports, customer/supplier accounts, purchasing, settlement, EMI, campaign, catalogue, return-entry/list and master-administration screens require an unscoped relevant grant. They do not pretend to provide per-store partitioning for shared accounts or multi-store documents. Some guarded action capabilities (for example a store-authorized walk-in return) are broader than the currently available scoped UI.
- Department-only grants fail closed on workflows that do not carry department scope. Department-scoped end-to-end operation is not claimed. Navigation may still display links that the server denies; a full role-aware navigation redesign was outside S3.
- Explicit super-admin grants permit ownership administration, but instance backups additionally require the protected legacy owner/super-admin account marker. A role grant alone does not turn someone into the server operator. Owner marker changes use ownership transfer.
- Revocation/lock/deactivation applies on subsequent server authorization checks, including an existing session. This is not cancellation of an already-authorized in-flight request or deletion of a previously downloaded document.

## Remaining risks and deferred acceptance

- No local prerequisite blocker remains for bounded S3. Phase 2 must run lint, complete tests, production build and browser acceptance against one frozen source snapshot. The earlier S4 build predates these changes.
- Browser navigation, HTTP middleware/server-action dispatch, production cookie/TLS behavior, real email delivery and provider integrations were not exercised here. Real cookie validation is covered at the auth API/helper level, not a browser journey.
- Empty-instance successful LAN bootstrap, fresh-cluster initialization, actual `pg_dump`/restore, backup provenance and Windows/cloud installation acceptance remain Phase 2/3 checks. Successful new-business onboarding was tested against the isolated database, but it is a different path from first-install LAN bootstrap.
- Instance backups are server-operator artifacts. `BACKUP_DIR` must remain server-controlled and contain backups belonging to that single-business installation, not historical/mixed-business dumps. The request-time ownership/business-count gate does not inspect an existing dump or prove isolation across simultaneous provisioning; backups for multi-business installations remain offline operator work. No restore or concurrent-provisioning backup safety claim is made.
- Email side effects still lack a durable outbox/retry system; delivery failure can leave a created/reset employee needing operator assistance. No deployment credentials were invented.
- Employee-ID lockout now counts concurrent failures atomically. Distributed/per-IP abuse limiting and denial-of-service resilience still require deployment review; a three-guess account lock can itself be abused. This session did not redesign Better Auth or add a new identity system.
- Earlier failed cleanup left only disposable S3 fixture data in the release-test database; final suite cleanup passed. No production cleanup was attempted.
- Existing dependency advisory decisions, accounting limits, clean-machine packaging, cloud recovery and seller-owned external setup remain in their respective release documents. None is waived by S3.

Not run in this scope: a migration command (no S3 schema changes), a full workspace test/lint suite, a production build, browser suite, actual backup/restore, packaging, public deployment, real email or live payments.
